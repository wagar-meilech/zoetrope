## Recommended fleet architecture

This is a proposal, not existing behavior. Add a small top-level `Console` owning `FleetState`, the active view/focus, persistent work/question state, and one selected `App` (optionally a bounded cache later). Keep a distinct `FleetFlow` projection whose nodes represent project groups, session roots and expanded child agents. Every identity must include provider + root session + agent; local `main` alone is not globally unique. Do not fabricate one giant `SessionModel` or mix every session's replay items into one timeline. The existing agent graph is specialized to one session and stable local node IDs. Source: [graph projection](../../src/state/graph.rs#L17).

Launch into the global graph; use a single `h` press to include/exclude history and `/` for local search. Preserve selection, expansion, query and viewport when toggling. Search matches project/title/session ID/agent label and retains ancestors so results remain a graph. Selecting a session enters the existing replay/detail component; returning restores the fleet graph. Global history remains one graph, rather than a separate list of historical recordings. A focused text editor must consume ordinary letters, `q`, `h` and `/` before global shortcuts.

Build a metadata index asynchronously and refresh it incrementally; materialize expanded children and load full timelines on demand. This keeps startup and memory bounded without an additional model pass. Persisting the index avoids reparsing all past recordings just to search titles. Keep current runtime status separate from transcript transport: an old mtime or `Transport::Idle` does not prove completed work. Preserve a visible unknown/offline status when runtime facts are absent.

There are two discovery gaps before calling this “everything that happened”: Codex scans only `$CODEX_HOME/sessions`, not archived sessions; Claude's sweep enumerates root files, with children expanded by `open`/`rescan`. The prior facts also identify incorrect classification of some internal Codex guardian helpers. Extend archive discovery and parent classification deliberately. Pin an explicit session with `Target::Path` or full ID; `Target::Here` follows newer sessions and `SessionReset` currently adopts the new identity, so that behavior must not override a user's fleet selection. Sources: [Codex roots](../../src/provider/codex/discovery.rs#L164), [Claude roots](../../src/provider/claude/discovery.rs#L180), [reset semantics](../../src/state/mod.rs#L460), [target semantics](../../src/tailer/mod.rs#L65).

## Goal/checklist and persistent-question minimum

No current `FactKind`, `SessionInfo`, Codex wire event or `SessionModel` represents goals, criteria, questions or draft answers. Do not overload the generic info-row store. Add a small typed work projection fed by explicit local edits, structured runtime events and supported transcript records; keep durable storage/effects native. Sources: [fact vocabulary](../../src/fact.rs#L89), [info store](../../src/state/info.rs#L14), [Codex event vocabulary](../../src/provider/codex/wire.rs#L317).

- A goal needs stable identity, objective, scope/revision, criteria with stable IDs, and verification entries referring to evidence (command result, document, or explicit user confirmation). Show verified criteria / current criteria; no criteria means “criteria not set,” without a fabricated percentage. A completed native plan step is a recorded claim, not automatically acceptance evidence. Retain scope revisions visibly. Timestamp authored changes/evidence so a historical detail view can avoid displaying future completion as though it had already happened.
- A question needs provider/thread/turn/item/question identity, original wording/options, original request binding, optional draft selections/text, and explicit unanswered/answered/dismissed plus delivery state. Persist creation and every draft edit atomically through a single native writer before session navigation/quit. Loading, focus changes, Escape and restart never choose a default or submit. Keep unanswered records when a runtime request expires; mark delivery unavailable and require an explicit new delivery action. A JSON-RPC request binding is connection-local, so it must not be blindly replayed after reconnect.
- A top-level questions inbox and target badges should be independent of whichever session `App` is loaded. Delivered responses from Codex can reconcile the same durable record; an unsupported read-only transcript remains observation-only. Criterion/question edits require no summarizing model call. Reuse existing commentary for meaningful purposes; keep routine read/write paths as expandable technical details.

These are import seams, not proof of client attachment or delivery support. ## Generated Markdown and actual installed previewer

Codex `Item::FileChange` already retains a path-keyed `changes` map, but the provider reduces it to a truncated human summary; Claude `Write`/`Edit` inputs likewise become short paths. These summaries cannot reliably identify documents: they can be truncated, basename-only, delete operations, failed attempts, or raw shell commands. Add structured artifact observations at the provider boundary with full path, owning target, source call/time, operation and observed result. Resolve relative paths against the recorded command/thread cwd; do not parse rendered summaries. Track successful create/update separately from attempted writes/deletes and stat a file before offering to open it. Shell/Python writes often lack structured file-change events: support an explicit artifact registration/import path and report partial discovery rather than claiming completeness. Reading a Markdown file is not creation evidence. Sources: [Codex file-change wire](../../src/provider/codex/wire.rs#L460), [lossy reduction](../../src/provider/codex/mod.rs#L346), [patch basename summary](../../src/provider/codex/mod.rs#L461), [Claude tool summary](../../src/provider/claude/mod.rs#L428).

The user's installed plugin is **AnandShah.mdreader 0.0.8, “MD Reader”**, not an extension literally named md-render. Its installed manifest contributes `mdreader.preview` (side-by-side) and `mdreader.fullRender` (in place), activated on Markdown/command invocation. No `customEditors` contribution appears in this plugin's metadata. The publisher documents opening a `.md` file then using those commands/icons. Sources: installed manifest (`/Users/melikhov/.vscode/extensions/anandshah.mdreader-0.0.8/package.json`, inspected locally), installation registry (`/Users/melikhov/.vscode/extensions/extensions.json`, inspected locally), [publisher README](https://github.com/AnandShah10/MDReader#usage).

`/usr/local/bin/code --help` reports VS Code **1.142.0** and supports file paths, `--reuse-window`, `--goto`, and extension listing, but no public `--command` flag. The official CLI also documents `vscode://file/...` for files. Both establish file opening, not invoking MD Reader. VS Code's public `executeCommand` API can invoke another extension's contributed command, and `registerUriHandler` lets an extension receive an external `vscode://publisher.extension/...` URI. Thus an explicit tiny VS Code bridge could open/show the selected document then invoke `mdreader.fullRender`; serialize those operations so the correct document is active. This needs a bridge or a new plugin capability; there is no verified MD Reader external launch URI. Do not promise that `code --command mdreader.fullRender` or opening `command:mdreader.fullRender` in an OS browser works. Sources: [CLI](https://code.visualstudio.com/docs/configure/command-line), [command API and command-URI context](https://code.visualstudio.com/api/extension-guides/command), [URI handler API](https://code.visualstudio.com/api/references/vscode-api#window.registerUriHandler).

Concrete bridge proposal (not installed): a minimal extension with provisional identity `wagar.zoetrope-preview` registers one `UriHandler` for `vscode://wagar.zoetrope-preview/open?uri=<encoded-file-URI>`. Its handler decodes the chosen file URI, awaits `workspace.openTextDocument`, awaits `window.showTextDocument` so that exact Markdown document is active, then awaits `commands.executeCommand('mdreader.fullRender')`. It checks the installed MD Reader extension/command and surfaces a clear error if unavailable; fallback built-in preview can be an explicit setting. The native effect invokes the OS URI opener with argument arrays (on macOS `Command::new("open").arg(uri)`), never a shell command string. Its status should say “Requested VS Code preview” unless an acknowledgment protocol is added: successful OS dispatch does not prove a rendered panel. [Public document/editor API](https://code.visualstudio.com/api/references/vscode-api), [built-in Markdown fallback](https://code.visualstudio.com/docs/languages/markdown).

Without the bridge, the native effect can already open the chosen existing path with `code --reuse-window <path>` using `Command` arguments and offer the MD Reader command name. Automatic render should only be advertised after bridge integration is tested. No GUI launch or preview was attempted here.
